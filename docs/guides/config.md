# Config shape, key by key

> **When to read this:** Read before adding, renaming or retuning a config key, or before editing the shipped `config.yaml`. Every value it ships carries its measured rationale in its own comment, and those values are per-deployment: a second deployment tunes its own.

## Current config shape

`config/config.yaml` is hot-reloaded on change, together with its overlay
siblings `config/sources.yaml` (curated sources) and `config/private.yaml`
(crawler-managed sources) — both append to `subscriptions.sources`. The `/`
request still takes its `subscription_url` and allowed countries from HTTP
query params; the `subscriptions` block only configures the `/stable.txt`
worker. The crawler reads `config/sources.yaml` and `config.yaml` itself too, at
`CRAWL_CURATED` (a comma-separated list, default
`/config/sources.yaml,/config/config.yaml`), for the NAMES its mint must not collide with
(`curatedNames`, `internal/crawl/crawl.go:1354`) and the URLs it must not mirror (`curatedURLs`,
`:1393`); it never crawls those entries and never writes either file. A
missing file there is normal and silent, while a read or parse failure warns
naming that file and the cycle goes on with the remaining paths — so it mints
without that file's names and may collide with them, and denies without that
file's URLs and may mirror a source already curated by hand as a managed entry.

Unknown keys are rejected: `config.yaml` and both overlays decode with
`yaml.KnownFields(true)`, so a typo fails the load naming the key instead of
silently falling back to the default. An empty or comment-only overlay still
loads. The crawler's narrow read above is the one exception, and
deliberately so: `curatedFile` (`internal/crawl/crawl.go:1338`) decodes
`subscriptions.sources[].name` and `.url` alone and ignores every key `config.Load`
owns, so a crawler build holds no opinion about a schema that is not its. That
is also why one struct reads both paths: `config.yaml` keeps its own sources
under the same key.

Important keys:

- `server.listen`
- `server.metrics_listen` — internal Prometheus `/metrics` endpoint (default `:9090`; docker-compose publishes it loopback-only on `127.0.0.1:9091`, never public)
- `geo.geofeed.refresh_interval` (default 24h when unset, explicit `0` = load once and never refresh) / `geo.geofeed.sources[].url` / `geo.geofeed.sources[].type` (`raw` or `gzip`). A source must exist only when something ASKS the provider a question — a `{type: country}` filter (whose provider defaults to geofeed) or an annotate chain naming it — and the loader refuses a config that references geofeed without listing one: `geo.geofeed.sources must contain at least one source: a country filter or annotate chain references the geofeed provider` (`Config.validateGeofeed`, `config.go:1852`, `referencesGeofeed` at `:1866`); a deployment whose chain is cloudflare/dbip/registry only, or asn/cidr filters only, legitimately carries none. **A reserved non-country row is a miss in every CSV parser, geofeed, dbip and registry alike**: `ZZ` is the source's own "cannot attribute" marker and `EU` ripencc's region code for allocations no one country holds, and both drop the row (`parseCountry`, `geofeed/dbip.go:114`), so neither can index a range that answers ahead of a database with a real country
- `geo.dbip.url` / `geo.dbip.refresh_interval` — DB-IP Country Lite monthly gzip CSV (`{yyyy-mm}`-templated URL, default built-in, 24h refresh; unlike the geofeed sibling, an explicit `0` means that same default — a month-stamped mirror frozen for the process lifetime is never what an operator wants, and a non-positive interval also blocks the retry a failed initial download arms); in-memory IP→country DB for the `dbip` annotate provider, built only when an annotate chain references it
- `geo.registry.urls[]` / `geo.registry.refresh_interval` — the five RIR delegated-extended files (defaults built-in, 24h refresh; explicit `0` = that default, as for `geo.dbip`); in-memory registration-country DB for the `registry` annotate provider, built only when referenced. **APNIC's file comes from `ftp.lacnic.net`, not `ftp.apnic.net`, and that is not cosmetic.** APNIC's own host answers the ClientHello without echoing the legacy session ID RFC 8446 4.1.3 requires, so `crypto/tls` aborts with "server did not echo the legacy session ID" (curl: "invalid session id" / connection reset) — the RIR then drops out of the build with `sources_failed=1` and the database loads 4 of 5 registries. Measured cost of that one dead URL: 255972 ranges instead of 330937, and 97.30% of the addresses behind the configured subscriptions placed instead of 99.85%. **LACNIC rather than the obvious RIPE copy is also not cosmetic**: both serve the file byte-identically under APNIC's own published `.md5` (`077c5ac4…`, checked against both mirrors and APNIC's `.md5` over FTP), so the tiebreak is single-host concentration. `ripencc` already comes from `ftp.ripe.net`; adding `apnic` there puts 201810 of 330937 ranges = 61.0% behind one outage, while `ftp.lacnic.net` leaves the worst host at ripencc's own 126845 = 38.3% — the floor no mirror choice can beat — with `ftp.lacnic.net` itself only second at 108784 = 32.9% — and `newGeoDB` at STARTUP takes the partial build with only a Warn, so that cliff is live. Byte-identity is a statement about the instant it was checked and NOT about freshness: a mirror is a copy re-cut on the upstream's schedule, so `LoadRegistry` logs each source's header serial (`serial=20260804` for apnic/lacnic/afrinic, a unix timestamp for ripencc and unix ms for arin — monotonic per source, not comparable across them) as an observable for lag. Nothing gates on it. Do not "fix" the URL back to the direct host, and do not "tidy" it over to the RIPE one
- `geo.asn.timeout` / `geo.asn.cache_ttl` — Team-Cymru ASN lookups, in-memory TTL cache (default 24h). **`asn` is not in the shipped `annotate` chain and re-adding it needs a new measurement, not a hunch.** Cymru's `origin.asn.cymru.com` redistributes over DNS the same RIR delegation data `registry` already holds in RAM, so it is a registry lookup with a network hop, not a geolocation source: measured over every address behind every configured subscription it was a strict SUBSET of a complete `registry` (zero countries it placed that registry did not, zero disagreements where both answered, and its disagreement rate against `dbip` was indistinguishable from `registry`'s), and behind the shipped chain its MARGINAL contribution was zero hits — `dbip` sits two steps ahead at ~99.85% coverage, and the residue is unroutable sinkhole / RFC 5737+2544 space Cymru correctly has no record for. Dropping it from the chain added no `[GEO:??]`. What it uniquely carries is the AS **name**, which no local database has, so `{type: asn}` deny patterns and `{type: country, provider: asn}` stay live and stay tested. The two leaves bind ONLY when one of those consumers is armed: the shipped filters list and annotate chain arm none, so tuning `geo.asn.timeout` / `geo.asn.cache_ttl` today changes no lookup (the shipped config.yaml says so in its own comment) — unarmed, no Cymru resolver is built and no key is read
- `resolver.timeout`
- `resolver.address` — upstream DNS server, passed verbatim to the dialer, so it MUST be `host:port` (`1.1.1.1:53`); a portless value is rejected at load, because it dials nothing and would drop every node as a DNS failure. The port is range-checked numerically too (`1..65535`): `resolver.address "1.1.1.1:99999"` produces the exact total DNS outage one typo later, so it is refused with `port "99999" is outside 1-65535; a value outside it dials nothing and drops every node as a DNS failure` rather than accepted. Empty keeps the system resolver
- `resolver.cache_ttl` / `resolver.cache_negative_ttl` (DNS TTL cache)
- `filters` — ONE ordered list for both stages. IP-stage entries (`type: country` with `provider: geofeed|asn`; `type: asn` with `deny_patterns`; `type: cidr` with `urls` + `file_type` + `refresh_interval`) run per node in preprocess on both `/` and the worker; through-node entries (`type: gemini`/`claude`/`chatgpt`/`tidal`/`bandwidth`) run post-probe in the stable worker only, and every one of them is a gate that drops. **Each through-node TYPE is a singleton, exactly like `cidr`**: a second gemini/claude/chatgpt/tidal/bandwidth entry is refused at load (`filters[i]: only one <type> filter is supported`, `validateFilters`, `config.go:1355`) — the stable worker renders one Prometheus series per entry, so two entries of one type would publish duplicate series in a single scrape and the gate's own counts would silently disagree — where `country` and `asn` entries repeat legally (`DeniedCountries` expands over every country entry; asn deny patterns chain). `exclude_groups`/`exclude_countries` on a `country` entry are **worker-only** — their single consumer is `config.Config.DeniedCountries()`, which feeds the `/stable.txt` worker; on `/` the country constraint comes from the query params alone, and it is enforceable only by a `{type: country}` entry (either provider) or a `{type: asn}` one — a deployment with neither (an empty list or a cidr-only one) cannot serve a country-gated request at all, and `GET /` answers it `400` with `no country-capable filter configured (filters[].type: country or asn): cannot honor countries/groups/exclude_countries/exclude_groups` rather than 200 with a list the parameters never narrowed (the snapshot's `CountryFilter`, from `config.CountryFilterConfigured`, `config.go:399`). A `cidr` entry is an ALLOW-list of IPv4 ranges downloaded from `urls` and unioned (`file_type` `raw`|`gzip`, default `raw`; `refresh_interval` unset or an explicit `0` means 24h, as for `geo.dbip`, negative rejected); it reads nothing from the request, so it is the one IP-stage entry whose verdict is identical on `/` and the worker. Its drops book `Stats.CIDRDrop` / `cidr_drop=` / `stable_source_dropped_nodes{reason="cidr"}`
- **The IP-stage order is load-bearing, not cosmetic, and nothing validates it.** `buildFilters` appends in written order and `processNode` returns at the first filter that empties the IP slice, so a cheap local gate belongs ahead of one that makes a network call per IP. The case that matters is `cidr` before `asn` (and before `{type: country, provider: asn}`): written the other way round, `ASNFilter.Process` spends a Cymru round trip per IP on nodes the allow-list discards one step later — 54535 of the measured pool's 59558 nodes. `config/config.yaml`, the only shipped config carrying a `cidr` entry, puts it FIRST in `filters:` — commented out since the 2026-08-14 verdict the entry itself records (`:43-79`, ahead of `- type: country` at `:80`) — and the list's header comment states the rule where a reader meets the list (`:37-41`). This stays a documented rule rather than a validator, because a validator would have to encode a cost model it has no business owning
- `annotate` — ordered tag list (`tag: GEO` is the only accepted tag; it takes `providers:`, an ordered chain of `cloudflare|geofeed|dbip|registry|asn` — first provider that resolves wins, all-miss renders `??`) prepended to node names on both `/` and `/stable.txt`; empty list disables annotation. One accepted tag does not make the LIST redundant: entries render in order and may repeat, so two `GEO` entries with different chains publish two tags — and the country `Annotate` RETURNS (the code `BuildPayload` writes into `Survivor.Country`, which the worker's gauges count) is the country the FIRST RENDERED tag carries, so a lead `[GEO:??]` books the zero code even when a later entry resolved: the node lands in `stable_geo_unknown_nodes` and nowhere in `stable_kept_country_nodes` (annotator.go's `tookLead`), and the empty list is a distinct mode rather than a milder one. **Repetition reaches BOTH stages.** `preprocess.countryChainOrder` builds the country FILTER's provider order by concatenating EVERY `GEO` entry's chain in written order, de-duplicated by first occurrence, so the filter's provider set is the union of what the entries name and repetition changes only what is RENDERED. Measured on an IP the geofeed cannot place and DB-IP puts in DE, one entry chaining `[geofeed, dbip]` and two entries (`[geofeed]` then `[dbip]`) reach the same FILTER verdict — kept under `countries=DE`, dropped under `exclude_countries=DE` — and differ only in the tag, `[GEO:DE]` against `[GEO:??][GEO:DE]`, and in the country booked: the split config's node carries a `??` LEAD, so it counts as geo-unknown even though a later entry resolved it — `BuildPayload`/`select.go` never sees `DE`, and the node is absent from `stable_kept_country_nodes{country="DE"}` (a reader trusting the second tag would overcount that series by exactly these nodes). A tag never overrides a drop either way: the filter, not the render, is the verdict's source. `cloudflare` is the only provider that is not consulted offline: it is a geo-IP database like the rest, but it is asked about the egress the node reported for itself, which exists only in the worker's post-probe stage, so on `/` it always misses and the chain falls through. `config.Config.AnnotateUsesProvider(config.ProviderCloudflare)` is what arms that probe — an offline-only chain never spends a request on it. The retired singular `provider:` key is rejected as an unknown key by the strict decode. `- tag: IP` and `- tag: ASN` fail the load as unknown tags (`validateAnnotate`, `config.go:1510-1514`); `rewrite.isKnownTag` still recognises `[IP:…]` and `[ASN:…]` on the STRIP side, deliberately, so an upstream-authored address or AS attribution is removed instead of riding along. Note that `asn` the PROVIDER and `{type: asn}` the FILTER are live and load-bearing; only the TAG is rejected.
- `geoblock.db_path` / `geoblock.ttl` (SQLite per-host geo-block list; default TTL 720h)
- `geoblock.gemini.*` / `geoblock.claude.*` / `geoblock.chatgpt.*` / `geoblock.tidal.*` (`endpoint`, `timeout`, `concurrency`; plus `marker` for gemini/claude/chatgpt, `model` + `api_key`/`key_file`/`key_var` + `rate_limit` for gemini, `version` for claude) — base params for the `gemini`/`claude`/`chatgpt`/`tidal` node-filters; enabled by listing `{type: gemini}` / `{type: claude}` / `{type: chatgpt}` / `{type: tidal}` in `filters` (a filter entry may override these per-field). **Every non-empty `endpoint` leaf — the four geoblock sub-blocks and a filter entry's override — is validated at load to be an absolute http(s) URL with a host** (`geoblock.gemini.endpoint: must be an absolute http(s) URL, got %q`; `filters[i].endpoint: …`): these are the URL leaves the through-node checks dial (`stable.hostPort`), the last leaves that had no load-time validation, and one typo dropped every node the gate saw as unreachable before the round gave the batch verdict a plausibility breaker. Empty means "inherit the built-in", so the guard only ever sees operator-written values. The `tidal` gate is the odd one out twice over. It has no refusal marker: where Tidal refuses an egress the request dies at the CDN (403 + HTML, measured from a RU egress), so the gate is **fail-closed on the status alone** — kept only on 2xx, and since redirects are not followed a 3xx interstitial is a refusal too. The body is deliberately not read (the country it reports gates where a subscription can be bought, not where an existing subscriber streams), so the gate answers only "did the request get through" and a 2xx from an ISP block page or captive portal counts as passed. It also never writes to the geoblock store (a bare status code is too weak a signal to persist host-wide for the store's TTL).
- The `gemini` gate CANNOT be made keyless, and a rejected key must never read as "not blocked". Measured against `generativelanguage.googleapis.com` from a geo-blocked egress: no key -> `403` "Method doesn't allow unregistered callers"; junk key (query param or `x-goog-api-key`) -> `400 API_KEY_INVALID`; valid key -> `400 FAILED_PRECONDITION` + the location marker. The API resolves caller identity, then key validity, and only then the location precondition, so the verdict this gate reads is invisible without a working credential — hence the classifier counts every answer that carries NO location verdict as inconclusive (`geminiInconclusive`): only a 2xx (all gates passed) and the marker-400 (the location refusal this gate drops on) are conclusive; 401/403/404/429, `API_KEY_INVALID`, a 5xx server fault, an unfollowed redirect and any reworded refusal were all answered before the verdict existed or without readable evidence of it, and those nodes are KEPT UNVERIFIED. And since the 2026-09 round a keyless gemini gate cannot even boot silently off: the LOAD refuses an armed entry whose merged key material is empty (`filters[i] (type gemini): the gate needs a key -- set api_key, or key_file + key_var, on the entry or on geoblock.gemini; without one every geo-block claim it makes is vacuous`), and APPLY refuses one whose declared key_file is unreadable or lacks key_var (`gemini gate is configured but its key cannot be resolved` / `resolves no key`) — the boot refuses, the reload keeps the previous settings — so the "configured but disabled" state that used to boot clean now exists only in wiring that bypasses config. Warning about them was never enough — measured on the production host it fired every cycle (`nodes=22 of=306`, then `nodes=7 of=285`) with nothing on the dashboard able to tell a working gate from a credential-broken one — so the count is also PUBLISHED, as `stable_gemini_gate_checks` / `stable_gemini_gate_unverified_checks` / `stable_gemini_gate_enabled` (`stable.GeminiReport`). Those nodes are kept, so the count MUST NOT ride `FilterReport.Dropped`. Keyless substitutes are country-list guesses, not this check: `gemini.google.com/app` and `aistudio.google.com/welcome` both answered `200` from that same blocked egress, and the supported-country list is documented at `ai.google.dev/gemini-api/docs/available-regions` (RU/BY/CN/HK/MO/IR/KP/CU/SY/AF/MM absent)
- The gemini gate GETs the model RESOURCE (`GET /v1beta/models/<model>?key=`), not `:generateContent`, and the two shapes disagree about a retired model: measured 2026-09-03 on `gemini-2.0-flash`, the POST answers `404` "no longer available ... use models/gemini-3.6-flash" while the GET answers `200` through an allowed egress and `400 FAILED_PRECONDITION` + the location marker through a blocked one. A retirement notice from the POST shape is therefore not a reason to bump `geoblock.gemini.model`, but it is a standing risk: a `404` is `geminiInconclusive`, so the day the resource stops serving, the gate keeps every survivor UNVERIFIED instead of failing. What that counter reads on a healthy pool is dominated by the READ quota, not by node-side refusals. The resource reads draw on `generativelanguage.googleapis.com/model_requests`, whose limit `ModelRequestsPerMinutePerProjectPerRegion` is 200/min per project per region (measured 2026-09-03 with the production key: 500 GETs at concurrency 8 finished in 20s and 202 returned `429 RESOURCE_EXHAUSTED`), and the gate fires one request per surviving node — 400-550 a cycle — so an unpaced gate blows the ceiling and the classified/unverified fingerprint degrades with the pool: 217/2, 338/85, 378/124, 423/166, 506/265, successes capping near 250 because the quota, not the pool, decides. The earlier 80-of-80 host-egress sample (no `429`, no `RESOURCE_EXHAUSTED`) proved nothing: 80 requests in 1.7s is simply under the per-minute ceiling. Hence `rate_limit` (default 150 = 75% of the measured limit, 0 means the default): it paces request STARTS so a cycle stays under the quota and every survivor reaches the verdict. The genuinely node-side residual is ~2%, not the 26-52% the raw unverified share suggests — over 163 published nodes probed sequentially (under the quota), 136 answered `200`, 19 returned the location block, 5 failed TLS (counted unreachable, not unverified) and 3 returned Google's HTML `403` for their egress.
- `geo.cloudflare.*` (`timeout`, `concurrency`; default 15s, 8) — the cdn-cgi/trace probe behind the `cloudflare` ANNOTATE provider, not a filter type: it gates nothing, drops nobody, and is armed by naming `cloudflare` in an `annotate` chain. It sits under `geo.` with the other geo databases because that is what it is — Cloudflare's own geo-IP database, whose verdict is the `loc=` line the tag carries. What differs from its siblings is the ADDRESS it is asked about: they place the address the RESOLVER returned, and 41% of the pool's named hosts sit in Cloudflare's shared anycast ranges, which terminate in many countries at once, so the tag described Cloudflare's registration while traffic left from the origin (measured: 47 of 102 published tags corrected). `ip=` is the means, not the published value — the trace buys the right address to ask about, not a more honest database. **There is no `endpoint` key**, deliberately: `stable.parseTrace`/`validCountry` encode Cloudflare's documented reserved `loc` values (`XX`, `T1`) and its uppercase convention, so no other VENDOR's endpoint could satisfy the parser and every cross-vendor value would fail SILENTLY, as an unanswered node (another Cloudflare-fronted host does parse — `/cdn-cgi/trace` is served on every domain Cloudflare proxies — so that substitution is made in the constant). Two limits remain: it never runs on `/` (no post-probe stage there), and it does not fix the `type: country` FILTER, which judges the resolved address in preprocess before any probe exists. **Reload class is `live-worker`, not the `live-processor` its `geo.*` neighbours carry** — the gate follows the CONSUMER (`config.ProberChanged`, `stable.filterAndMeasureEgress`), never the namespace; `internal/reload/reload_coverage_test.go` pins both halves
- `deadcache.ttl` (in-memory cache of probe-dead nodes; default 2h, explicit `0` disables; skips re-probing; not persisted). The block key is the endpoint's `server:port` AND the address the IP stage resolved for it that cycle (`deadKey{addr, ip}`): a hostname re-pointed to a different address is a different server for the cache's purposes, and skipping it unprobed would keep a healthy node out of the list for the whole jittered [3h, 4.5h) TTL. The dead-cache WRITE carries the same whole-pool plausibility breaker as the pre-check and the through-node gates (see monitoring.md): a cycle where nearly every probed node failed leaves the cache unchanged — the fault reads as our egress, not the pool
- `groups.<name>` (country sets referenced by requests and `exclude_groups`)
- `subscriptions.interval` and every `subscriptions.check.*` param are validated on every load, even with no sources configured (they all arrive from the overlays here, and a list-gated check would let a bad value boot clean and then fail every later reload). **An explicit `0` is a built-in default, never a value** — on `subscriptions.interval` (0 -> 30m) and on every `subscriptions.check.*` knob except `max_fail` (`rounds` 0 -> 5, `timeout` 0 -> 2s, `source_timeout` 0 -> 120s, `max_avg_ms` 0 -> 1000, `concurrency` 0 -> 16): `applyDefaults` rebinds the zero BEFORE the validation floors run (`config.go:1573`), so a floor can only ever catch a negative — the floors' own wording ("must be at least 1", "must be positive") is the tell. `max_fail` is deliberately NEVER defaulted: its `0` is the strictest setting (every round must pass) and the loader only checks it against `rounds` (`max_fail must be within [0, rounds)`). This convention is the OPPOSITE of the disable-style zeros elsewhere in the file (`deadcache.ttl 0` disables the cache, bandwidth `min_mbps 0` removes the speed floor, geofeed `refresh_interval 0` loads once and never refreshes) — the shipped config.yaml says so in its own comment. Two budget rules then guard a cycle against absurd-but-valid knob pairs, because `RunOnce` has no wall-clock deadline (`checkCycleBudget`, `config.go:1640`): `check.rounds × check.timeout` must not exceed the interval — compared by DIVISION so `rounds: 1e9, timeout: 24h` is refused before the duration product can overflow — and `check.source_timeout` must not exceed it (sources fetch at most 16 at a time, each capped at that value, so one hung source alone can stall the fetch phase for the whole of it). The product rule is a conservative absurd-knob guard, not a feasibility proof: rounds × timeout is the per-node worst case only when the attempts serialize at concurrency 1, the probe runs the rounds concurrently behind `check.concurrency`, so a single hung node holds it for about one timeout and the whole-phase bound scales with the live node count, which no config-only check can express. The interval itself has a 1m floor (`subscriptions.interval must be at least 1m0s`) that a rebound 0 sails past
- `subscriptions.sources[].name` + `url` *or* inline `body` (base64/raw node URIs; used by the crawler's harvest, whose source is the fixed name `inline`, which nothing reserves — see the end of this bullet), plus `managed` (`internal/config/config.go:639`), which only the crawler writes, `feed` (`:644`), which the crawler writes at mint and a curated entry may also set, and `hwid` (`:650`), which only an operator writes. Two entries may not share a URL **under the same `hwid`**, whatever files they came from: the fetch identity is url + hwid, because `x-hwid` changes what the panel serves (a header-less fetch of a device-limited URL answers a placeholder where the same URL with the header returns the real nodes) — so a differing `hwid` (the empty one included) is a distinct fetch whose payload can contribute, and `validateSources` refuses only the identical pair (`subscriptions.sources.<name>: url <url> is already fetched as <owner> with the same hwid "<hwid>"; sources sharing a url AND hwid fetch the same payload twice and the later one contributes no node`) — Merge's first-source-wins dedupe would keep only the earlier name's nodes while every cycle fetched the URL twice. `managed: true` marks an entry the crawler minted and may rewrite or prune; ABSENT means hand-added and sheltered, so an operator who forgets it is safe by default — with one exception, the load-time migration, which adopts three pre-cutover name shapes (`tg-<slug>-<6hex>`, `tg-<10hex>` and `tg-inline`) even unmarked, because before the cutover that shape WAS the mark (`needsAdoption`, `internal/crawl/crawl.go:1509`; `docs/guides/sources.md` has the reasoning) — and it is REJECTED on a `config.yaml` or `sources.yaml` entry — those two are curated by definition — by a per-file gate rather than by load order, each naming the file whose entries it holds: Load refuses the mark in config.yaml's own list in a pre-merge pass (`config.go:1093`), `mergeSourcesOverlay` refuses it in sources.yaml's entries as it loads them (`config.go:1184`), and `validateSources` over the merged list (`config.go:1663`) stays as the second gate for any other statement order — all raising one wording (`errManagedInCuratedFile`, `config.go:1162`) so the error names the offending file and entry whichever gate caught it. `feed` records the Telegram channel a harvested source came from, because the name cannot be folded back onto one; it grants nothing and only groups the `feed` Prometheus label, so a curated entry may set it and an empty value means the source names itself. **`hwid` is what gets a source past a panel's HWID device limit, and its ABSENCE never reads as a failure.** Non-empty, it rides as the `x-hwid` request header on THAT source's subscription fetch in the worker AND on the crawler's liveness fetch of the same managed entry (the recheck pass carries each entry's HWID per URL, `crawl.go:558-564`) — a device-limited panel serves a placeholder to a header-less fetch, so a header-less liveness probe would condemn a source the worker keeps publishing — and on no other request: `GET /` never sends one (that endpoint takes a URL from query params and has no source config an hwid could come from), a crawler-discovered candidate has no entry yet, and the standalone `classify` CLI sends none. Measured 2026-08-28 against a Remnawave panel advertising `x-hwid-active: true`, the header-less fetch answered **200** carrying a single placeholder node (`vless://00000000-…-000000000000@0.0.0.0:1#Ошибка HWID`) where the same URL with the header returned 828 B carrying 2 real nodes. So what a missing `hwid` buys is not an error but a source that fetches 200, publishes nothing and books no error anywhere — `nodeless-2xx` in the crawler's own vocabulary. No status is bad and no log line reads wrong; the one signal is that source's own `stable_source_published_nodes` sitting at 0 with `stable_source_nodes_total` at 1 — and that is a gauge to query rather than a row to spot, since the three per-source dashboard tables (panels 20, 8, 22) are each `topk(25)` by `stable_source_valid_nodes` and a source whose whole contribution is one placeholder sorts below the cut on any pool with more feeds than that (`docs/guides/monitoring.md` has the measured 110 buckets). A malformed value would land in the same place — the panel ignores an `x-hwid` it cannot parse rather than complaining about it — but the loader refuses that one first, naming the source. The vendor docs (<https://docs.rw/docs/features/hwid-device-limit/>) promise a **404** when the header is absent; the measured panel sends 200 instead, so the status line never says so. The RESPONSE HEADERS do: measured 2026-08-28, the header-less fetch came back carrying `x-hwid-not-supported: true` and `x-hwid-limit: true` beside `x-hwid-active: true`, where the fetch with a valid value carried `x-hwid-active: true` alone — the panel has sent those two since v2.7.5 and documents a third, `x-hwid-max-devices-reached`, for a subscription out of device slots. Nothing here reads any of them: `fetch.BytesWithTypeHWID` returns the body, and widening it to surface headers is the churn the one-named-field decision exists to avoid, so the per-source gauges above remain the signal. `x-hwid` is the only header those docs require — `x-device-os`/`x-ver-os`/`x-device-model` are optional and deliberately not implemented — and the panel validates it against `^[a-zA-Z0-9=-]{10,64}$` (panel v3.0.0+), a shape the loader enforces as well (`validateSourceHWID`, `internal/config/config.go:1711`, the regex `sourceHWIDRe` declared at `:131`), so a value the panel would refuse fails the load naming the source rather than silently publishing nothing. The value is the operator's to invent and not the panel's to issue — any string of that shape is accepted, e.g. `hwid: abcdef0123456789`, and the panel registers it as a NEW DEVICE, so it works only while the subscription has a free device slot. Each DISTINCT value spends one, so set it once and never rotate it: a rotation burns a slot and, once they are gone, silently reverts the source to the placeholder. An `hwid` on a source with no `url` (an inline `body:` entry) is REJECTED at load (`:1718-1722`), nothing being fetched there for a header to ride on. **`inline` is the crawler's own aggregate name, and no validator keeps you off it.** That entry (`inlineSourceName`, `internal/crawl/crawl.go:1155`) holds the inline node URIs harvested across messages and channels, and it is the one managed name derived from nothing, so it is the one you can take by accident: nothing announces the crawler's namespace. Take it in `config/private.yaml` and the crawler skips its own inline entry rather than write a duplicate beside yours (RunOnce's duplicate guard, `crawl.go:455-460`), so the price is the inline harvest itself — that cycle's and every later one's while you hold the name. Take it in a GIT-TRACKED file and you get neither warning nor yield: both files are read, but into the mint's taken-name set and the URL deny funnel, and the fixed `inline` — a `body:` entry with no `url:`, built by `buildInlineSource` (`crawl.go:1169`) — enters neither, so the crawler cannot see the collision, writes `inline` to `private.yaml` regardless, and the merged list carries the name twice, which `config.Load` refuses: the SERVICE DOES NOT START until one of the two goes. `docs/guides/sources.md` has the log lines, the citations and why reserving the literal name was refused.
- `subscriptions.check.*` (`rounds`, `timeout`, `max_fail`, `max_avg_ms`, `test_url`, `expected_status`, `concurrency`, `source_timeout`) — probe params; through-node filters and exclusions live in the top-level `filters` list. Mostly URL-test params, with one exception worth knowing before you retune `timeout`: it ALSO sets the reachability pre-check's dial budget (`precheckDialBudget` = `timeout` / `precheckAttempts`, so both attempts share exactly one round's budget). That coupling is deliberate, and the safety argument is narrower than it first looks, so state it exactly: the deadline each attempt gets is `timeout / precheckAttempts`, i.e. HALF a round, not a whole one. What makes half a round safe is that TCP + TLS + the `GET` through the tunnel is about three round trips, so a bare handshake that eats half a round cannot leave room for the other two. The guarantee is about the SYN and nothing else: it does not extend to a node failing exactly one round, which `max_fail: 1` makes survivable while condemnation is terminal and dead-cached for a jittered [3h, 4.5h). A resolution failure does not condemn: the pre-check fails OPEN on a `*net.DNSError` and lets the URL test decide, because its bare `net.Dialer` resolves through Go's uncached resolver while mihomo's `URLTest` reads a stale-serving LRU that costs at most one blocking lookup per process. A fixed budget cannot serve every deployment: the 500ms constant this replaced was 8x tighter than the second instance's own `max_avg_ms: 4000`, and it silently deleted nodes that instance was tuned to keep. That instance was retired 2026-08-26 and the coupling is what keeps the next one safe, which now takes a test to see rather than a config to read: the shipped `timeout: 1000ms` (`config/config.yaml:263`) over `precheckAttempts` 2 derives to exactly that 500ms, so `TestPrecheckBudgetTracksTheDefaultTimeout` strips the `timeout` line from the shipped config to tell derived from hardcoded, while `TestPrecheckBudgetCoversShippedLatencyGates` reads that config as it stands.
- `subscriptions.snapshot_path` — where the worker persists the list it just published, reloaded at startup — but ONLY when subscriptions are enabled: an empty source list at startup is the deliberate disable, and serving the previous run's snapshot then would answer 200 with a stale list and no worker ever to replace it (`restoreStableList` gates on `SubscriptionsEnabled()`, `app.go:193-199`) — so with sources configured, `/stable.txt` serves the last good list instead of `503` while the first cycle runs (measured 58 minutes on a 68266-node pool). Empty disables. The shipped value is `/config/.stable-snapshot.json`: `./config` (`docker-compose.yaml:14`) is that service's only WRITABLE host bind mount — its other one, the agenix secret at line 16, is a read-only file — and uid 1000 already writes `.geoblock.db` into it — `.crawler-state.json` sits there too, but the crawler container writes that one as root (`docker-compose.yaml:26`) — so persistence adds no volume and no host-side provisioning. It is absolute because every OTHER path key the SHIPPED file sets is (`geoblock.db_path`, `geoblock.gemini.key_file`), and the runtime image is `WORKDIR /`. A path under `/tmp` would land in the container's OWN writable layer, which `docker compose up -d` recreates after a build — it would survive `docker restart` but not the redeploy those 58 minutes came from. The accepted cost is that the snapshot now outlives a host reboot too, the same guarantee its two neighbours already have. Writing it into the watched directory does NOT self-trigger a reload: `reload.Watcher` adds that directory to fsnotify, but `matches` compares each event against the three exact overlay paths, so the per-cycle temp-create + rename is ignored. There is no TTL, deliberately — the in-memory rule already keeps the last good list through failing cycles, and the age stays visible in `X-Stable-Stats updated=`. It takes no validator beyond the strict decoder, exactly like the three other path keys in the SCHEMA (`geoblock.db_path`, `geoblock.gemini.key_file`, `filters[].key_file`) — a wider population than the two the shipped file sets, and `routes.md` enumerates that one. **Startup-only:** it is in `config.StoresChanged` and EXCLUDED from `config.SubscriptionsChanged`, so a reload warns instead of re-applying the worker — the only key in the block that behaves that way
- `fetch.timeout` — per-subscription fetch deadline for the WORKER (default 3s, deliberately fail-fast: sixteen sources fetch concurrently under per-source deadlines of minutes, so one hung source must not hold its slot). `GET /`'s on-demand download does NOT use it — the single fetch inherits the request's own 60s deadline, so a slow-but-healthy subscription is not cut at 3s with most of the advertised request budget unused (`preprocess.Filter` passes no sub-budget; the 504 on expiry is the request's, `internal/server/server.go`). The crawler's per-URL liveness probes mirror the WORKER's default rather than reading config.yaml — `Options.FetchTimeout`, fed from `CRAWL_FETCH_TIMEOUT` (default 3s, `main.go`'s `defaultCrawlFetchTimeout`), falling back to `defaultProbeTimeout` in the package — so the probes live inside whatever budget the worker fetches under. That mirror is also the divergence: tuning `subscriptions.fetch.timeout` in config.yaml does NOT reach the crawler, and an operator who tunes it must set `CRAWL_FETCH_TIMEOUT` to match, or the crawler judges sources on a budget the worker no longer uses (the comment at `internal/crawl/crawl.go:37-47` says it in full)
